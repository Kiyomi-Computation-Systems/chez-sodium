## 1. What M2 delivers

- **Three verbs,** exported by `(chez-sodium)`, each with its signature comment:

  ```scheme

  ;; blake2b : Bytevector [Natural] [Bytevector] -> Bytevector   ; input, size, key
  ;; constant-time-bytevector=? : Bytevector Bytevector -> Boolean
  ```

  `missing-api` row and row 22 (ADR-0002, amended): `randombytes_buf`, `crypto_generichash`, five

  decoy that answers sizes no release has (§4.1, items 7 and 8).

  its three names in `(chez-sodium)` (§4.2, item 2; the owner's).

- **A check of the decoy's pointer rule,** reading its source (§4.1, item 9).
- **The verbs' shape held as data,** as `test-native`'s E rows hold native's: every check before
  the section, and no raise inside it (§4.1, item 10).

## 4. Decisions

Each gives a recommendation, its evidence, and whose it is.

### 4.1 Owed to M2 (`progress.md`)

1. **Brief §4.3's ranges, restated here, and recorded in ADR-0007's amendment** (§4.3):
   - `random-bytes n`: `n` from 0 to the cap. At 0 it answers `#vu8()`, which has no byte to
     share, and calls no C: Chez has one empty bytevector (slice 0's review).
   - `blake2b input [size] [key]`: `size` from `_bytes_min` to `_bytes_max`, default `_bytes`; a
     key, when given, from `_keybytes_min` to `_keybytes_max` bytes, and an empty key refused.
     Each bound is read from libsodium (item 7), and each is checked before C, since C accepts
     sizes and keys of 1 to 15 bytes. With no key, the key is a one-byte block, length 0.
   - `constant-time-bytevector=? a b`: once each operand is within the cap (item 4), lengths
     that differ answer `#f` and call no C. Equal lengths, 0 included, go to `sodium_memcmp` over
     the whole length.
   - A key needs a size: the optionals are positional, as brief §4 writes them.
2. **The bindings: eight, each plain** (§4.2, item 1). The forms, each the whole second argument
   of `bind-required`, in this order, after `sodium_memzero`, with the prototype in 1.0.22's
   `sodium.h` spelling (§5.1):

   ```scheme
   (foreign-procedure "randombytes_buf" (uptr size_t) void)
   (foreign-procedure "crypto_generichash" (uptr size_t uptr unsigned-64 uptr size_t) int)
   (foreign-procedure "crypto_generichash_bytes" () size_t)
   (foreign-procedure "crypto_generichash_bytes_min" () size_t)
   (foreign-procedure "crypto_generichash_bytes_max" () size_t)
   (foreign-procedure "crypto_generichash_keybytes_min" () size_t)
   (foreign-procedure "crypto_generichash_keybytes_max" () size_t)
   (foreign-procedure "sodium_memcmp" (uptr uptr size_t) int)
   ```

   - Each is plain: the cap bounds every call (§5.1 times them).
   - **This plan's,** within ADR-0001, ADR-0002 and ADR-0005.
3. **Row 24 reaches a verb's blocks through the decoy.**
   - **The problem.** M1's child names a block from inside PROC, which a verb never hands out.
     The interposer cannot wrap `crypto_generichash` in front of the real library: Chez binds each
     name from the most recently loaded object, which is libsodium, even with the interposer
     preloaded (slice 0's review probed a preloaded `sodium_memcmp`, and libsodium's won).
   - **Recommendation:** the decoy names its blocks. Each of the decoy's M2 entries calls
     `watch_set` on every pointer it is handed, with the length it is handed, through a weak
     symbol: in the wipe child, whose `LD_PRELOAD` is the interposer, it resolves; everywhere
     else it is NULL, and the decoy skips it. The call and the pattern's write go through the
     pointer's `volatile uintptr_t`, as item 9 requires.
   - **The interposer keeps every name in order, with its length,** and answers the list of
     (length verdict) pairs. A second child of `test-wipe`, its library the decoy, runs each verb
     and asserts each call's whole list: keyed `blake2b` of 3 bytes at size 32 with a 16-byte key
     is `((32 1) (3 1) (16 1))`, so a block the decoy does not name makes the list shorter.
   - **Every witnessed block holds a non-zero byte before its wipe.** The decoy writes `A5` over
     every output, under every switch (slice 1), and every input, key and operand the child
     passes holds a non-zero byte. The decoy's `sodium_memzero` zeroes what it is given, so the
     wipe is still the binding's call, through the binding's entry point.
   - **What it cannot witness:** a block named with length 0, as the unkeyed key and a length-0
     compare's operands are, reads 1 whatever happens; `random-bytes 0` makes no block. M1's row
     24 holds `call-with-bytes`' one-byte block for an empty bytevector.
   - **A standing positive control,** for each of the three M2 entries: called through native's
     raw binding on blocks the child frees with no wipe, each named block reads 2.
   - Structurally, rule (m) and E7 already make every block a `call-with-block` block, and M1's
     row 24 holds that helper's wipe. This row holds the verbs end to end.
   - **Measured first,** in slice 2: the weak symbol resolves in the wipe child, and is NULL in a
     library-loading child; `-Wall -Werror` accepts the test of it.
   - **This plan's,** by ADR-0008 and ADR-0011; ADR-0011's amendment records it.
4. **The input cap: `input-cap`, 65536, in `(chez-sodium private cap)`.**
   - Each verb checks it before its section: `random-bytes`' `n`, `blake2b`'s `input`, each of the
     compare's operands. 65536 is accepted, 65537 refused, for each of the four.
   - **The compare checks both operands' types and the cap before it compares lengths,** so an
     operand over the cap raises even against a short one: every byte input is capped, whatever
     path the verb then takes.
   - A library of its own, since M3's password verbs need it and should not import M2's verbs.
   - **This plan's,** by ADR-0007, decision 5.
5. **The refusals' shape.** Each verb checks its parameters left to right, each one's type
   before its range, and refuses the first mistake, before any block. The irritants lead with the
   rule's symbol (ADR-0006, decision 5); a secret is shown as `(kind K)` through `refuse-secret`;
   `n` and `size` are shown by `shown-value`:

   | Verb | Parameter | Mistake | Irritants |
   |---|---|---|---|
   | `random-bytes` | `n` | not an exact natural | `(not-a-natural n V)` |
   | | | over the cap | `(over-the-cap n V)` |
   | `blake2b` | `input` | not a bytevector | `(not-a-bytevector input (kind K))` |
   | | | over the cap | `(over-the-cap input (kind bytevector))` |
   | | `size` | not an exact natural | `(not-a-natural size V)` |
   | | | out of range | `(size-out-of-range size V)` |
   | | `key` | not a bytevector | `(not-a-bytevector key (kind K))` |
   | | | empty | `(empty-key key (kind bytevector))` |
   | | | length out of range | `(key-length-out-of-range key (kind bytevector))` |
   | `constant-time-bytevector=?` | `a`, then `b` | not a bytevector | `(not-a-bytevector a (kind K))` |
   | | | over the cap | `(over-the-cap a (kind bytevector))` |

   - Each is an assertion violation, its `&who` the verb. An over-cap key is refused by the
     key's range, which ends at libsodium's `_keybytes_max`, 64 at every release; a row holds
     that bound, and `_bytes_max`, within the cap (slice 2's review, M2S2-F11).
   - `call-with-bytes`' own `(not-a-bytevector bytes (kind K))` stays, a net no verb reaches.
   - Each verb joins `test-never-loads`' `verb-names`, and its export row fails by name until it
     does.
   - **The symbols are this plan's,** the shape ADR-0006's. `over-the-cap` and `not-a-natural`
     are M3's too.
6. **Where the verbs live: `(chez-sodium private byte-verbs)`, beside native.**
   - Native stays the load, the raw bindings and the helpers. The verbs library holds no
     `foreign-procedure`, `foreign-ref`, `foreign-set!` or block of its own: rule (f) keeps the
     first three in native, and rule (m) keeps every block in `call-with-block`. It reads
     foreign memory only through native's `foreign-bytes`.
   - **Its imports are held whole** (item 10): `check-seam` lets any library import
     `critical-section`, so only that row keeps a verb from making a section of its own.
   - `test-never-loads`' loaders row, asserted whole, gains it; `check-nothreads` refuses it by
     name.
   - Evidence: chez-sqlite3's verbs live beside its native, each family in its own library.
     Native here is 487 lines, and M3 adds the password verbs beside it in the same way.
   - **The owner's,** with the names (§4.4).
7. **How a verb reads a size: once, at the load.**
   - A new step 7 of native's load calls each size function once, after step 6 has bound every
     entry point, and records the answer. The verbs check against the recorded numbers before
     their sections, in pure Scheme.
   - Evidence: the sizes are fixed for a build of libsodium. A call at each verb would be a C
     call outside the section, or five more inside it. The decoy's log shows the five calls
     once, at the load, in order.
   - **ADR-0001 decision 2's check, by behaviour:** the decoy's `sizes-other` answers 33, 8, 80,
     9 and 81, which no release answers, and whose bounds lie outside the real ones. Through it,
     `blake2b`'s default answer is 33 bytes; sizes 7 and 81 are refused, and 8 and 80 accepted;
     keys of 8 and 82 bytes are refused, and 9 and 81 accepted. A size written in Scheme, in
     place of the read one or beside it, fails one of these. Each row asserts the decoy's log
     line whole, as `crypto_generichash(p,33,p,3,p,9)`, so it also sees which length goes where.
   - **Only `crypto_generichash`'s five sizes** are read at the load. M3's own constants decide
     their own reading.
   - **The owner's,** since it amends ADR-0002, decision 4 (§4.3), and confirmed with the
     records.
8. **No constants half in `test-constants`.** The oracle prints each size function's answer and
   its header macro, compiled against the header the suite's lane names, and `test-native` holds
   native's recorded sizes to both, and to brief §3.4's numbers. That is row 22 for the sizes, on
   every lane, in the one suite that already reads the oracle. **This plan's.**
9. **The decoy's pointer rule, held by `test-decoy-source`.**
   - It reads every `tests/*.c` that includes `sodium.h`, as text, with comments and string
     literals stripped, matching whole identifiers. In each definition of a function `sodium.h`
     declares, a `sodium_*`, `randombytes_*` or `crypto_*` one, each pointer parameter, written
     with a `*` or as an array `T NAME[...]`, occurs in the body exactly once, as `(uintptr_t)
     NAME` in a `volatile uintptr_t` declaration. A declaration with no body is not read, and the
     decoy's own helpers, such as `called`, are outside the rule.
   - Evidence: a `-Werror` compile holds the rule only for a `nonnull` parameter, and `nonnull` is
     per function: at both releases it covers `randombytes_buf`'s `buf` and
     `crypto_generichash`'s `out`, and none of the other four pointers (§5.1).
   - Watched to fail on a planted ternary over a pointer, on a second use of one, and on an
     array parameter used plainly.
   - **This plan's;** M1's slice 3 review owed it (S3-F3).
10. **The verbs' shape, read as data,** in `test-byte-verbs`, as `test-native`'s E rows read
    native (slice 0's review, M2S0-F3).
    - **Why a row, not a mutant.** `call-in-section`'s catch-all guard raises again, after the
      section, whatever THUNK raised. So a verb that raised inside its section, or refused a
      mistake there, behaves the same as one that does it after or before: the handler runs at
      depth 1, the counts are zero, and the decoy's log is empty. Only the text can tell.
    - **The rows:**
      - each verb's definition holds exactly one `call-in-section`, and every check, every
        `refuse-secret` and every `assertion-violation` comes before it;
      - the whole list of symbols inside each `call-in-section`'s argument, against a list
        written in the suite, so a helper called inside, local or top-level, shows by name;
        and no `lambda` outside the section's argument but `case-lambda`'s clauses (slice 2's
        review, M2S2-F1);
      - `input-cap` read once in `random-bytes` and `blake2b`, and twice in the compare;
      - no `raise`, `raise-sodium-failed`, `assertion-violation`, `refuse-secret` or `error`
        occurs inside `call-in-section`'s argument;
      - `byte-verbs`' and `cap`'s import clauses, whole: `require-threaded` first, and nothing
        from `(chezscheme)`;
      - under `src/`, the cap's literal 65536 occurs in `cap.sls` alone.
    - Watched to fail with the raise moved inside the section, a check moved after it, a second
      section, and a `critical-section` import.
    - **This plan's.**

### 4.2 New questions

1. **`crypto_generichash_keybytes` is not bound.**
   - **Recommendation:** bind five of the six size functions. `_keybytes`, the recommended key
     size, has no use: `blake2b` has no default key.
   - Evidence: the subset rule binds a function only for a named use, and each binding is more to
     test on every libsodium (ADR-0005). Brief §3.1 writes the family as `_keybytes*`.
   - **The owner's.** It amends brief §3.1 and §3.4, and ADR-0005 records it.
2. **`crypto_generichash` answering anything but 0 raises `&sodium-failed`.**
   - The binding's checks rule out every -1 libsodium answers (§5.1). If it answers -1 anyway,
     `blake2b` has no hash to answer: a -1 leaves `out` as it was.
   - **Recommendation:** `&sodium-failed`, its function `"crypto_generichash"`, its code the
     answer, its `&who` `blake2b`, raised after the section. Its first raise moves from M3 to M2,
     and `sodium-failed?`, `-function` and `-code` join `(chez-sodium)` now. Row 17's M2 half is
     the decoy's `generichash-fails`, under a guard for something else.
   - **Any answer but 0 is `&sodium-failed`,** its code the answer. The decoy has two codes,
     `generichash-fails`' -1 and `generichash-other`'s 1, so that no single value passes for
     failed, as `init-other` does for `sodium_init`; row 17 asserts the code whole.
   - Evidence: ADR-0006's tree makes every library condition a `&chez-sodium-error`, and
     `&sodium-failed` is "the verb, and what libsodium answered". The type is built; only its
     first case moves.
   - Alternatives: ignore the code, and answer what `out` holds; or an assertion violation, which
     would be no `&chez-sodium-error`.
   - **The owner's.** It amends ADR-0006, decision 3, ADR-0012, decision 2, brief §5 and the
     constraints.
3. **`constant-time-bytevector=?` answers `#t` only for 0.** Any other code is `#f`. The decoy's
   `memcmp-other` answers 1 for equal operands, and the verb answers `#f`: a verb that tested
   for -1 would answer `#t`. **This plan's.**
4. **Row 13's "every position varies":** 8 calls of 64 bytes, and each position takes at least
   two values. A right binding fails it with odds about 2⁻⁵⁰ a run. **This plan's.**
5. **Row 1's sources:**
   - RFC 7693's Appendix E self-test, run through `blake2b` alone: the outputs concatenated and
     hashed once to 32 bytes equal the RFC's published result, as its incremental hash would;
   - the BLAKE2 reference's `blake2b-kat.txt`, every entry, from a pinned commit, kept in
     `tests/fixtures/blake2b/`;
   - BLAKE2b-256 and -512 of `"abc"` and of the empty input, from a second implementation,
     Python's `hashlib`, measured once for this plan, and written in the suite;
   - three keyed hashes whose key length is not their size, from `hashlib`, measured the same
     way: a 16-byte key at size 32 and a 64-byte key at size 20, each over `"abc"`, and a 17-byte
     key at size 64 over the empty input (§5.1).

   The known answers hold one 64-byte key and 64-byte outputs, so they catch a dropped key and
   nothing about sizes; the self-test, at sizes 20 to 64 with keys as long, and `"abc"` at 256
   bits catch a wrong size and a truncation; and only the three keyed hashes catch a key length
   taken from the size (§5.1). **This plan's.** The files were fetched once,
   on the host, for §5.1, and slice 2 copies them.
6. **The out block is not filled.** `random-bytes` and `blake2b` make their output blocks with a
   FILL! that writes nothing: C writes every byte of a success, and a failure's block is never
   read. The block is wiped at the free, like any other. **This plan's.**

## 6. The slices

One PR each, in order. Each ends with a read-only adversarial review on Opus, and its fixes.
Each keeps a mutation log, `.plans/m2-slice-N-mutation-log.md`, in the form Guards, Mutation,
Result, Clean rerun.

**Every brief restates these** (M1's list, and what M1's reviews added):

- tests assert a reason symbol, who and irritants, and whole outputs: never a message;
- nothing raises inside a critical section or a critical `dynamic-wind` thunk;
- anything that can raise is computed under a guard, with a sentinel of its own. **Before the
  hand-back, grep every top-level definition of every suite for a call that can raise;**
- no expected value is `#f` from something that can raise;
- `let*` where one init must follow another; `for-each` for effects;
- every engine row references the library once before its first engine;
- every row that forks a thread which reaches the library references it once first;
- each suite ends with `(exit (suite-exit-status runner))`;
- a child that reaches native code starts through `gated-command`, and asserts `(valgrind . yes)`
  exactly when the gate asked; the wipe children, and `test-constants`' prototype check, a C
  program that calls no libsodium function, alone run outside (ADR-0011, amended);
- every new check is watched to fail before it counts, by a mutant in a whole copy of the tree,
  never in place, and the real file passes under each mutant;
- **for each row, name the call in its expected output that shows its claim;**
- an engine spends no ticks inside a section: assert the outcome at every fuel, never an expiry;
- a red run against a check that refuses the whole input proves no row: turn each rule off
  instead;
- a program naming an unbound identifier dies before its first line: watch new-export rows fail
  against stubs that are present and wrong;
- Valgrind logs carry the checkout's path: scrub them before committing;
- a witness has a standing positive control.

Builders are Sonnet, reviews Opus.
