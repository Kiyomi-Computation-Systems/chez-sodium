## 1. What M3 delivers

- **Three verbs and a constructor,** exported by `(chez-sodium)`, each with its signature
  comment:

  ```scheme
  ;; password-hash : String [Limits] -> String
  ;; password-verify : String String -> Boolean              ; hash, password
  ;; password-needs-rehash? : String [Limits] -> Boolean      ; hash
  ;; make-password-limits : Natural Natural -> Password-limits ; ops, memory in KiB
  ;;   Limits = (U 'interactive 'moderate 'sensitive Password-limits), by default 'interactive
  ```

- **Seventeen entry points,** each with its convention row, its prototype check, its decoy
  entry, its `missing-api` row and row 22 (ADR-0002, amended). There are the three password calls,
  two of them `__collect_safe`, and fourteen constants (§4.1, item 1; §4.2, item 1).
- **The constants, read once at the load** through libsodium's own functions. A decoy that
  answers values no release has holds that by behaviour (§4.1, item 6).
- **Two writers in native:**
  - `call-with-c-string` for the hash string, which ends in a 0;
  - `call-with-utf8` for the password, written straight into its block.

  Each bounds every write by its block, and answers a string changed mid-write as data
  (§4.1, item 2).
- **A pure library, `(chez-sodium private password-text)`,** holding the UTF-8 count, the hash
  string's pre-check and needs-rehash's prefix and `p=1` check. It loads no libsodium, so its
  rows run without one (§4.1, item 11).
- **Each verb's refusals** come before any block, each leading with its rule's symbol. A secret
  is named by its kind alone, and a bound is stated as numbers (§4.1, items 9 and 10).
- **`crypto_pwhash_str`'s `&sodium-failed`,** raised after the section, its code the answer
  (§4.1, item 3; §4.2, item 3).
- **Row 19, collect-safe by behaviour:** decoy calls block on a FIFO while another thread's
  collection finishes, from inside the verb's critical section (§4.1, item 4).
- **Row 4, the C oracle both ways,** through its new hex mode (§4.1, item 4).
- **Row 24 for the password verbs' blocks,** through the decoy and the `free()` interposer
  (§4.1, item 8).
- **The verbs' shape held as data,** as `test-byte-verbs`' S1 to S5 hold the byte verbs (§4.1,
  item 7).

## 4. Decisions

Each gives a recommendation, its evidence, and whose it is.

### 4.1 Owed to M3 (`progress.md`)

1. **The bindings: seventeen.**
   - **The forms,** each the whole second argument of `bind-required`, in this order, after
     `sodium_memcmp`:

     ```scheme
     (foreign-procedure __collect_safe "crypto_pwhash_str" (uptr uptr unsigned-64 unsigned-64 size_t) int)
     (foreign-procedure __collect_safe "crypto_pwhash_str_verify" (uptr uptr unsigned-64) int)
     (foreign-procedure "crypto_pwhash_str_needs_rehash" (uptr unsigned-64 size_t) int)
     (foreign-procedure "crypto_pwhash_strbytes" () size_t)
     (foreign-procedure "crypto_pwhash_strprefix" () uptr)
     (foreign-procedure "crypto_pwhash_opslimit_min" () size_t)
     (foreign-procedure "crypto_pwhash_opslimit_max" () size_t)
     (foreign-procedure "crypto_pwhash_opslimit_interactive" () size_t)
     (foreign-procedure "crypto_pwhash_opslimit_moderate" () size_t)
     (foreign-procedure "crypto_pwhash_opslimit_sensitive" () size_t)
     (foreign-procedure "crypto_pwhash_memlimit_min" () size_t)
     (foreign-procedure "crypto_pwhash_memlimit_max" () size_t)
     (foreign-procedure "crypto_pwhash_memlimit_interactive" () size_t)
     (foreign-procedure "crypto_pwhash_memlimit_moderate" () size_t)
     (foreign-procedure "crypto_pwhash_memlimit_sensitive" () size_t)
     (foreign-procedure "crypto_pwhash_passwd_min" () size_t)
     (foreign-procedure "crypto_pwhash_passwd_max" () size_t)
     ```

   - **Collect-safe:** `crypto_pwhash_str` and `crypto_pwhash_str_verify`, the two that run
     long (brief §6.4). `crypto_pwhash_str_needs_rehash` parses and compares, and is plain.
   - **The convention table** already has a `CONVENTION` column, which M2's rows leave empty.
     A `foreign-procedure` form's convention must match its row, so a collect-safe call bound
     plain fails by name (X-M3). Row 19 holds it by behaviour too.
   - **The allow-lists gain no type:** `uptr`, `unsigned-64`, `size_t` and `int` are there
     already.
   - **This plan's,** within ADR-0001, ADR-0002 and ADR-0005, but for `_passwd_min` and
     `_passwd_max` (§4.2, item 1).
2. **The writers: `call-with-c-string` and `call-with-utf8`, in native.**
   - **`call-with-c-string : Symbol String (Positive-Integer -> A) (-> A) -> A`.**
     - PROC gets a block of N+1 bytes holding the string's N characters, one byte each, then a
       0.
     - Each character is checked as it is written. One outside U+0021 to U+007E, the pre-check's
       range, means the string changed since the verb's pre-check, so CHANGED's answer is the
       helper's, and PROC is not called.
     - Chez's strings cannot change length, so the block always fits.
   - **`call-with-utf8 : Symbol String Natural (Positive-Integer -> A) (-> A) -> A`.**
     - PROC gets a block of `(max 1 N)` bytes holding the string's UTF-8, where N is the count
       the verb took before its section.
     - Each character's bytes are written only if they fit in what is left of N. The write ends
       with exactly N bytes written. If not, the string changed between the count and the
       write, so CHANGED's answer is the helper's, and PROC is not called.
     - An empty string gets a one-byte block written 0, never NULL (row 11).
     - It encodes from `char->integer`, one to four bytes, with no `string->utf8`: no Scheme
       bytevector holds a password (ADR-0008). A Chez character is a Unicode scalar value, so
       every character has an encoding (§5.1).
   - **`foreign-ascii-string : Natural Natural -> (U String #f)`.**
     - It reads the bytes at ADDRESS before the first 0 within N, each a character of its own.
     - It answers `#f` when there is no 0 within N, or a byte is 0x80 or above.
     - `password-hash` reads its out block with it, N being `strbytes`.
   - **Each helper raises nothing inside the section** for a string that changed: it answers
     CHANGED's value. Its own checks come before any block, and are a net no verb reaches, as
     `call-with-bytes`' are:
     - a WHO that is no symbol, by `check-who`;
     - a string that is no string, through `refuse-secret` from WHO, irritants
       `(not-a-string string (kind K))`;
     - for `call-with-utf8`, an N that is no exact natural, by `shown-value`;
     - a PROC or CHANGED that is no procedure, by `shown-value`.
   - **Why a CHANGED thunk, not a symbol:** PROC's answer could be any value, so no answer of
     its own can mean "changed".
   - **This plan's,** by ADR-0001 and ADR-0008. The progress ledger owed it, from v0.1.1's
     `call-with-c-string`, which makes two Scheme copies of its string.
3. **`crypto_pwhash_str`'s `&sodium-failed`.**
   - `password-hash` raises it after the section, its function `"crypto_pwhash_str"`, its code
     the answer, its `&who` `password-hash`.
   - It is raised for any answer but 0, as `crypto_generichash`'s is (§4.2, item 3).
   - **It is also raised when the answer is 0 and the out block holds no readable string,**
     with code 0: `foreign-ascii-string` answers `#f`. No release does this, so the decoy's
     `pwhash-str-unreadable` reaches it: it answers 0 and leaves `out` all `A5`, with no 0
     within `strbytes`. Its row expects `(failed password-hash "crypto_pwhash_str" 0)`.
   - `raise-sodium-failed`'s fixed message, "libsodium answered a failure for a call that
     passed its checks", becomes "libsodium gave no result for a call that passed its checks",
     true of code 0 too. No row reads it.
   - Row 17's M3 half: the decoy's `pwhash-str-fails` answers -1, and `pwhash-str-other` 1, each
     under a guard for something else. The outer guard catches the `&sodium-failed` itself,
     with its code whole.
   - **The owner's,** with §4.2, item 3: accepted, 2026-11-24.
4. **The oracle's hex mode, and the FIFO decoy.**
   - **Row 4.**
     - `libsodium-oracle PATH hash HEX` hashes, at libsodium's minimum limits, the bytes HEX
       spells, and prints `(hash . "STRING")`.
     - `libsodium-oracle PATH verify STRING HEX` prints `(verify . CODE)`.
     - `test-password-oracle` does both ways, in gated children, for three passwords: a
       non-ASCII one, `"a\x0;b"`, and the empty one.
     - C hashes and Scheme verifies; Scheme hashes and C verifies. Each pair is also checked
       false with the password's last byte changed, and the empty password against `"a"`, so a
       verify that answers 0 for anything fails.
   - **Row 19.**
     - Under the decoy's `pwhash-blocks`, `crypto_pwhash_str` and `crypto_pwhash_str_verify`
       each first create the marker file `$CHEZ_SODIUM_DECOY_FIFO.entered`, then open the FIFO
       named by `CHEZ_SODIUM_DECOY_FIFO` read-only, so each blocks until a writer opens it. Each
       then reads to the end, and answers as the control does. With the variable unset, each
       answers -1 at once, so a row that forgot it fails.
     - The child, `collect-probe`, references the library once, then forks a thread that calls
       the verb. Every row that forks a thread which reaches the library references it once
       first (ADR-0007, amended).
     - **The main thread waits until the call is in C.** It polls for the marker, with a bound,
       then pauses 1 s, as chez-sqlite3's row does once its opener is calling. Only then does it
       run `collect-rendezvous`, record its time, and open the FIFO for writing, which releases
       the call. Without the wait the rendezvous can finish before the call reaches C, and a
       plain binding passes: slice 0's review saw it pass 8 runs of 8 (M3S0-F1).
     - **The child starts the watchdog once the marker appears,** a shell that opens the FIFO
       after 10 s, so a plain binding cannot hang the suite and a slow start under Valgrind
       does not eat into the bound. The verdict names who released the call.
     - **Its standing control:** a test-side plain binding of the decoy's
       `crypto_pwhash_str_verify`, called the same way inside `critical-section`, is released by
       the watchdog.
     - The verb's call is inside its section, so the row holds what M3 relies on: a collect-safe
       call inside a critical section still lets another thread collect (§5.1).
     - It runs gated, under Valgrind in `test-memory`. The rendezvous must end within 5 s: the
       worst measured was 17 ms under Valgrind, and a plain binding holds it until the
       watchdog's 10 s (§5.1). The watchdog's bound is 10 s.
   - **This plan's,** by ADR-0011; its amendment records the switches.
5. **Rows 11, 15, 16, 18, 22 and 24 for the password verbs.**
   - **Row 11's password half:** `""` hashes and verifies `#t`, and `"a"` verifies `#f` against
     it. The decoy logs the empty password's pointer as `p` and its length as 0.
   - **Row 15:** item 9's table, each refusal also against the decoy's log, where the growth is
     empty. `length-out-of-range` is reachable only under `pwhash-limits-other`, since at every
     release the range holds the cap (§5.1).
   - **Row 16:** item 9's secrets, each passed as a secret-looking symbol, number and character
     list. No message or irritant holds any of it.
   - **Row 18:** each verb under an engine at every fuel, at the minimum limits. Each run answers
     right, raises nothing and leaves no live block.
   - **Row 22:** §5.1's codes, through native's raw bindings, on every lane.
   - **Row 24:** item 8.
   - **This plan's.**
6. **How M3's constants are read: once, at the load, in step 7.**
   - **Step 7 reads them.** After the five sizes, step 7 calls each of the fourteen constant
     functions once, in item 1's order, and records each answer.
     - `crypto_pwhash_strprefix`'s answer is read with `c-string->string`, which answers `#f`
       for NULL.
     - The verbs check against the recorded numbers before their sections, in Scheme.
   - **Evidence:** M2's sizes are read this way (ADR-0001, amended), and a constant is fixed for
     a build of libsodium. A call at each verb would be fourteen more C calls in the section, or
     calls outside it.
   - **The check, by behaviour.** The decoy's `pwhash-limits-other` answers values no release
     has, with bounds inside the real ones (§6, slice 1). Through it:
     - each bound is refused one past its edge and accepted at it;
     - the presets hash at the decoy's numbers, read from the log line;
     - the prefix is the decoy's;
     - `strbytes` is the decoy's out block's size: the growth's `sodium_memzero(p,160)` line
       shows it. The decoy writes `A5` over its own `strbytes`, so a block made from a Scheme 128
       is also a write past the block, which the gate sees. Its fixed string there is 140
       characters, so a reader bounded by a Scheme 128 finds no 0 and the hash fails, code 0.

     A constant written in Scheme, in place of the read one or beside it, fails one of these.
   - **A NULL prefix** is recorded as `#f`. Then `password-needs-rehash?` answers `#t` for every
     hash, without C, since no hash begins with the loaded prefix. The decoy's `strprefix-null`
     holds it.
   - **The constants are held to the library on every lane:** the oracle prints each function's
     answer and its header macro, and `test-native` holds native's to both, and to §5.1's
     numbers.
   - **Twins.** `opslimit_max` and `passwd_max` both answer 4294967295 at every release, and
     their macros are both `4294967295U`. So against a real library neither native reading one
     into the other's key, nor the oracle printing one under the other's name, can be seen. M2's
     closing review warned of this (M2-F1). As M2 fixed its sizes, so here: under
     `pwhash-limits-other`, whose ops maximum is 9 and password maximum 100, a gated oracle
     child and `refusal-probe --constants` each print the fourteen, asserted whole. A macro
     swapped with its twin cannot be held by any value, and this plan records it.
   - **The owner's,** since it amends ADR-0001 and ADR-0002 (§4.3): accepted, 2026-11-24.
7. **The shape rows for the password verbs,** in `test-password-verbs`, reading
   `password-verbs.sls` alone, as `test-byte-verbs`' S1 to S5 read `byte-verbs.sls`:
   - each verb's definition holds exactly one `call-in-section`, and every check, refusal and
     pre-check comes before it. `make-password-limits` holds none;
   - the whole list of symbols inside each section, against a list written in the suite, and no
     `lambda` outside it but `case-lambda`'s clauses;
   - no raise inside a section;
   - `input-cap` read the times the suite says;
   - `password-verbs`' and `password-text`'s import clauses, whole;
   - **no Scheme copy of a secret:** a row reads `password-text.sls` and `password-verbs.sls` as
     data and refuses `string->utf8`, `utf8->string`, `string->list`, `list->string`,
     `substring`, `string-copy`, `string->bytevector` and `bytevector-copy` anywhere in them,
     and `string-append` but inside a top-level definition of no parameters whose name ends in
     `-message`, which cannot see a verb's arguments. The value rows cannot see a copy:
     `string->utf8`'s length equals the summed widths on every string (§5.1).

   Watched to fail with the raise moved inside, a check moved after, a second section, a
   `critical-section` import, `utf8-length` through `string->utf8`, and a `substring` in the
   shape check. **This plan's.**
8. **Row 24 for the password verbs goes through the decoy.**
   - Each new decoy entry names every pointer it takes to the weak `watch_set`, through the
     pointer's `volatile uintptr_t` copy, with the block's length:
     - `crypto_pwhash_str`: `out` at `strbytes`, then `passwd` at `(max 1 passwdlen)`;
     - `crypto_pwhash_str_verify`: `str` at its `strlen` + 1, then `passwd`;
     - `crypto_pwhash_str_needs_rehash`: `str` at its `strlen` + 1.
   - `crypto_pwhash_str` writes `A5` over every byte of `out` before its string, under every
     switch, so the block is never zero before its wipe.
   - `test-wipe`'s second child runs each password verb at the decoy's limits, and asserts each
     call's whole list of (length verdict) pairs.
   - `test-decoy-source`'s list and `(library-loading)`'s `every-entry` gain the new entries.
   - **This plan's,** by ADR-0008 and ADR-0011, amended.
9. **The refusals.**
   - Each verb checks its parameters left to right, each one's type before its range, and
     refuses the first mistake, before any block. **Every refusal comes before the pre-check:**
     `(password-verify "\x0;bad" 'x)` is `not-a-string` for `password`, not `#f`. A row holds
     each such pair, and under the decoy `over-the-cap` comes before `length-out-of-range`, for
     a password of 65537 bytes.
   - The irritants lead with the rule's symbol. A secret is shown as `(kind K)` through
     `refuse-secret`. Numbers and preset names are shown by `shown-value`, which shows a string
     by its kind.

   | | `limits` | not a preset or limits | `(not-password-limits limits V)` |
   | `password-verify` | `hash` | not a string | `(not-a-string hash (kind K))` |

   - **Each is an assertion violation,** its `&who` the name.
   - **What is not refused:**
     - a hash string over the cap, or not printable ASCII, is answered: `#f` from
       `password-verify`, `#t` from `password-needs-rehash?`, without C;
     - a hash another thread changed during `password-needs-rehash?`'s call is answered `#t`,
       since it never raises because of the hash (ADR-0009, decision 3);
     - a symbol that is no preset is shown, since a preset's name is no secret.
   - **The bounds a refusal states,** through `refuse-secret`'s LOW and HIGH:
     - `over-the-cap`: 0 to `input-cap`;
     - `length-out-of-range`: `passwd_min` to `passwd_max`.

     Their messages say so in numbers.
   - **This plan's,** the shape ADR-0006's. `over-the-cap` and `not-a-natural` are M2's.
10. **R16 for the password verbs, and the every-file row.**
    - **R16.** Each refusal that states a bound, `over-the-cap` and `length-out-of-range` for
      `password` in the two verbs that take one, prints the same for three passwords:
      - two strings of one UTF-8 length, one of them non-ASCII, with different characters;
      - a third of another UTF-8 length.

      Two strings of one length must differ in content, and one of them must not be ASCII, so
      that a character count and a byte count differ. The print holds none of the first secret's
      text, searched as M2's R16 searches, and no decimal of its length.
      - **`over-the-cap`,** in `test-password-verbs`, in process: 65537 and 65538 bytes.
      - **`length-out-of-range`** is reachable only under `pwhash-limits-other`, so its R16 is in
        `test-library-loading-passwords`: 101 and 102 bytes, through `verb-probe`'s option that
        prints the whole condition. The empty password, below the decoy's minimum of 1, is one
        value, and is not varied, as M2's empty key is not.
    - **`refuse-secret`'s own bound refusals** are held by kind for a string passed where a bound
      goes. M2 holds it, and M3 adds no bound written by hand.
    - **The every-file row.** `test-decoy-source`'s every-file refusals run over every
      `tests/*.c`. A new C file, `collect-probe` needs none, joins it if one is written, and
      includes no local file.
    - **This plan's,** by ADR-0006, amended.
11. **The pure core: `(chez-sodium private password-text)`.**
    - **`utf8-length : String -> Natural`:** the sum of each character's UTF-8 width, from
      `char->integer`. The cap and the length range are checked against it, never through
      `string->utf8`.
    - **`readable-hash-string? : String -> Boolean`:** brief §4.1's pre-check. Every character
      is U+0021 to U+007E, which rules out U+0000, and the length is at most `input-cap`. The
      empty string fails it.
    - **`current-hash-shape? : String (U String #f) -> Boolean`:** brief §4.2's item 4, given the
      loaded prefix.
      - The hash begins with the prefix, then reads `v=` and digits, `$m=` and digits, `,t=`
        and digits, `,p=1$`, and then at least one more character.
      - Anything else is `#f`, and so is a `#f` prefix.
      - It is stricter than libsodium's parser, so a hash it refuses is merely rehashed, the
        safe direction.
    - **Pure:** no load, so `test-password-text` runs with no libsodium. `password-verbs` imports
      it.
    - **This plan's.** The functional core the project's guidelines ask for.

### 4.2 New questions

1. **`crypto_pwhash_passwd_min` and `_passwd_max` are bound, and checked.**
   - **The facts:** on all four libraries measured, `passwd_min` is 0 and `passwd_max` is
     4294967295 (§5.1). So today the cap is a password's only real bound.
   - **Recommendation:** bind both, as brief §3.1 lists them, and refuse a password whose UTF-8
     length is outside `passwd_min` to `passwd_max` as `length-out-of-range`, after the cap.
     The check would matter if a release ever raised the minimum:
     - an empty password would then make `crypto_pwhash_str` answer -1, which `password-hash`
       would raise as `&sodium-failed`, a memory failure;
     - `password-verify` would answer `#f` for a password that can never match.

     The decoy's `pwhash-limits-other` holds the check.
   - **Alternative:** leave both unbound, as `_keybytes` is, since no release's range binds. The
     cap would be the only bound, saving two bindings and their rows. Brief §3.1 and ADR-0005
     would record it.
   - **The owner's: bind and check,** 2026-11-24.
2. **`make-password-limits` checks its ranges when it is called.**
   - **Recommendation:** it refuses an `ops` or `memory-kib` outside libsodium's range at once,
     reading native's recorded bounds, so its first call runs the load. A `Password-limits` is
     then always in range, and the verbs check only that `limits` is a preset or one of these.
     - A configuration file's bad limits fail where they are read, not at the first login.
     - Memory runs from `memlimit_min` / 1024, rounded up, to `memlimit_max` / 1024, rounded
       down, in whole KiB. Every release and the decoy use whole KiB, so no row holds the
       rounding (§5.1).
   - **Alternative:** a constructor that loads nothing and checks types only, with the verbs
     checking ranges before each section. That is pure, but a bad limit then waits for its
     first use.
   - **The owner's: in `make-password-limits`,** 2026-11-24.
3. **Any answer but 0 from `crypto_pwhash_str` is `&sodium-failed`.**
   - libsodium answers -1 for limits out of range, which the checks rule out, and for no
     memory (§5.1). After a -1, `out` is all zeros, so there is no hash to answer.
   - **Recommendation:** any answer but 0 raises, its code the answer, as `crypto_generichash`'s
     does (ADR-0006, amended). The decoy answers -1 and 1, so that no single value passes for
     failed.
   - ADR-0006, decision 3, says "-1"; its M2 amendment says "anything but 0" for
     `crypto_generichash` alone. This makes the two cases one rule.
   - **The owner's.** It amends ADR-0006 and the constraints. Accepted, 2026-11-24.
4. **Techo's question: can `password-verify` tell short memory from a wrong password?**
   - **The ask:** Techo's login counts a `#f` as a failed try, and five lock the account. So on
     a server short of memory, the right password can lock its owner out. Its brief names two
     ways; Techo has a fallback, and asks for nothing by a date.
   - **The facts (§5.1):**
     - every case answers -1, at both releases;
     - **at 1.0.18, libsodium itself makes short memory a mismatch.** `argon2_verify` turns any
       failure of the hash into `ARGON2_VERIFY_MISMATCH` (`argon2.c`, line 258), and errno then
       reads `EINVAL`, as for a wrong password. Nothing the binding can read tells them apart;
     - at 1.0.22, `argon2_verify` keeps the allocation error (line 272), so errno reads `ENOMEM`
       for short memory and `EINVAL` for a wrong password. A string that fails to decode leaves
       errno as it was, 0 in the probe. Which release changed it was not measured.
   - **The routes, and what each costs:**
     - **errno.** It works only above the floor. It needs a binding of libc's
       `__errno_location`, which is not libsodium, read after a collect-safe call, where
       Chez's own return to Scheme may set errno first. Not measured, and not safe to rely on.
     - **Verify without the `_str` call** (Techo's first route). It needs `crypto_pwhash` and
       its algorithm constants, a parser and base64 decoder for the hash string, and a
       constant-time compare. That is a second argon2 string parser, which must accept what
       libsodium's accepts, the 136-character hash and argon2i among them, or it will refuse
       hashes that verify today. Every byte of it handles secrets.
     - **Ask for the memory again after a -1** (Techo's second route). It is a guess, and it
       can be wrong either way when memory changes in between.
   - **Recommendation:** no change in M3. `password-verify` answers `#f` for all three, as
     brief §4.1 and ADR-0006, item 4, decide. M4's documents say so, and say what a caller can
     do, Techo's fallback. A later release, once the floor is past the change, can revisit errno
     by a record.
   - **Alternative:** Techo's first route, as a slice of its own after M3's.
   - **The owner's: no change in M3,** 2026-11-24. Techo's session is told.
5. **`make-password-limits` is exported, and nothing else of its record.**
   - Brief §4 exports the constructor alone: no predicate, no accessors. A caller makes limits
     and hands them to a verb. Nothing in Techo reads them back.
   - ADR-0012, decision 2, says `(chez-sodium)` exports "never a `&` name or a constructor".
     That rule is about conditions: a caller must not build or extend ours. This plan reads it
     as "never a condition's `&` name or constructor", and ADR-0012's amendment says so.
   - The record type is opaque and sealed, and its type name is not exported, so no caller can
     make a `Password-limits` but through the constructor.
   - **The owner's,** since it amends ADR-0012: accepted, 2026-11-24.
6. **A string changed during the call is refused, after the section.**
   - Another thread may `string-set!` a password or a hash while a verb holds it. A character
     that changes width makes the count wrong. The writers then stop, before any write past the
     block, and answer CHANGED (§4.1, item 2).
   - **Recommendation:** after the section, `password-hash` and `password-verify` raise an
     assertion violation, `(changed-during-call P (kind string))`: the caller shared a mutable
     string across threads without a lock.
     - A change that keeps the UTF-8 length, or keeps a hash's characters in range, is not seen,
       and what was written is used, as a bytevector changed mid-copy is (ADR-0008).
     - `password-verify` refuses too, not `#f`: `#f` would read as a wrong password.
     - **`password-needs-rehash?` answers `#t` for a changed hash,** and raises nothing: it never
       raises because of the hash (ADR-0009, decision 3), and a hash it could not read whole is
       not current. Slice 0's review found the first draft raising there (M3S0-F5).
   - **This plan's,** within ADR-0006 and ADR-0009.
